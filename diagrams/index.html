CPF Board TextUs - System Architecture & Structure

This document provides an overview of the architecture and directory structure for the CPF Board TextUs application, a training simulator designed to help customer service officers master concepts relevant to providing accurate and efficient responses to customer inquiries about the Central Provident Fund (CPF) in Singapore.

Architecture Overview

The CPF Board TextUs application follows a modern, layered architecture that separates concerns and provides a scalable foundation for the training platform. The system is designed with the following key layers:

Frontend Layer (Next.js)

The frontend is built using Next.js, providing a responsive and interactive user interface for trainees, administrators, and managers. It includes several key components:

  • Dashboard: Displays performance metrics, recommended practice sessions, and quick access to start new sessions.
  • Chat Interface: Provides a real-time messaging interface for practice sessions with AI-simulated customers.
  • Scenario Browser: Allows users to select from available scenarios and configure practice sessions.
  • Admin Interface: Enables administrators to manage scenarios, customer profiles, and monitor system performance.

API Layer (FastAPI)

The API layer is implemented using FastAPI, a modern Python framework that supports async requests and provides OpenAPI documentation. Key components include:

  • Auth API: Handles user authentication, authorization, and session management.
  • Chat API: Manages chat messages and interactions between trainees and simulated customers.
  • WebSocket: Supports real-time chat functionality through WebSocket connections.
  • Scenario API: Provides endpoints for scenario management and selection.
  • Customer API: Handles customer profile management and customization.
  • Analytics API: Provides endpoints for performance analytics and reporting.

Services Layer

The services layer contains the core business logic of the application. Key components include:

  • Auth Service: Implements JWT-based authentication and rate limiting.
  • Conversation Scheduler: Manages chat conversations, including history tracking, WebSocket handling, and agent-based conversation management.
  • AI Service: Integrates with OpenAI for AI chat simulation and implements RAG (Retrieval Augmented Generation) for improved response accuracy.

Data Layer

The data layer handles persistent storage and caching for the application. Key components include:

  • PostgreSQL Database: Stores users, scenarios, customers, conversations, and analytics data. Provides full-text search capabilities for efficient data retrieval.
  • Redis Cache: Handles rate limiting, session management, and WebSocket state. Provides high-performance caching for temporary data.
  • Vector Database: Stores document embeddings for the RAG system and CPF knowledge base information to enhance AI responses.

External Integrations

The system integrates with external services:

  • OpenAI API: Provides AI models for simulating customer interactions and generating contextually appropriate responses.

Data Flow

The system follows a standard request-response pattern, with data flowing through the layers as follows:

  1. User requests originate from the Frontend Layer and are sent to the appropriate API endpoint.
  2. The API Layer validates the request and passes it to the relevant Service.
  3. The Service Layer processes the request, communicating with the Data Layer as needed.
  4. For AI-driven customer simulations, the AI Service communicates with the OpenAI API and retrieves context from the Vector Database.
  5. Responses flow back through the layers to the user interface.
  6. Real-time chat functionality utilizes WebSocket connections for immediate message delivery.

Monorepo Structure Overview

The CPF Board TextUs application uses a monorepo structure to organize its codebase, bringing together frontend, backend, and infrastructure components in a single repository. This approach simplifies development, deployment, and maintenance.

Documentation (/docs)

Contains project documentation including:

  • prd.md: Product Requirements Document detailing the application's purpose, features, and requirements.
  • architecture.md: Technical architecture documentation.
  • changelog.md: Record of changes and updates to the application.

Frontend (/frontend)

The Next.js-based frontend application with:

  • Configuration Files: package.json, next.config.js, tsconfig.json for project settings.
  • app/: Pages, layouts, routes, and client-side rendering components using Next.js App Router.
  • components/: Reusable UI components including dialogs, buttons, inputs, and cards.
  • lib/: Utilities, custom hooks, and API client for backend communication.

Backend (/backend)

The FastAPI-based backend with:

  • Configuration Files: pyproject.toml, requirements.txt for Python dependencies.
  • main.py: Application entry point and initialization.
  • api/: API route handlers for auth, chat, scenarios, and customers.
  • services/: Core business logic including auth, conversation management, and AI integration.
  • models/: Data models for users, scenarios, customers, and conversations.
  • db/: Database migrations, session management, and model definitions.
  • rag/: Retrieval Augmented Generation components including embeddings and vector storage.

Infrastructure (/infrastructure)

Deployment and infrastructure configuration:

  • docker-compose.yml: Local development environment setup.
  • docker/: Dockerfiles for frontend and backend containers.
  • k8s/: Kubernetes deployment files and service definitions for cloud deployment.
  • scripts/: Utility scripts for setup, deployment, and database migrations.

Project Files (Root Directory)

Root-level project files:

  • README.md: Project overview and getting started guide.
  • LICENSE: Project license information.
  • .gitignore: Git ignore rules for project.
  • .env.example: Example environment variable configuration.
  • .github/workflows/: CI/CD pipeline configuration for automated testing and deployment.

Key Relationships

The monorepo structure facilitates several important relationships between components:

  • The frontend's API client in the lib/ directory communicates with the backend API endpoints.
  • Documentation in docs/ describes the implementation in both frontend and backend.
  • Infrastructure components containerize and deploy both frontend and backend services.
  • CI/CD workflows in .github/workflows/ test and deploy all components together.
  • Shared types and interfaces can be maintained consistently across frontend and backend.

This monorepo structure offers the advantages of unified versioning, simplified dependency management, and coordinated deployments while maintaining clear separation of concerns between frontend and backend components.
